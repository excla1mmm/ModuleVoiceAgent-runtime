# Voice Agent runtime

[![CI/CD](https://github.com/excla1mmm/ModuleVoiceAgent-runtime/actions/workflows/ci-cd.yml/badge.svg)](https://github.com/excla1mmm/ModuleVoiceAgent-runtime/actions/workflows/ci-cd.yml)

Cloud side of the MikoPBX **ModuleVoiceAgent**: an AI voice secretary that answers calls on many PBXs.
Asterisk (chan_websocket, Asterisk 22) streams each call to this service over WSS; the service runs
Silero VAD, GigaAM v3 speech recognition, an OpenAI-compatible LLM and Piper speech synthesis, and tells
the PBX what to do with the call (transfer, callback request, goodbye).

Privacy model: the PBX is the source of truth. Agent data (prompt settings, directory, knowledge base)
and call results live **only in RAM** here; results can be read repeatedly and are deleted after the PBX acknowledges durable storage (or expire after
`VA_RESULT_TTL`). Logs carry technical fields only (no phone numbers, no transcripts unless
`VA_LOG_TRANSCRIPTS=true`). The LLM provider sees the prompt and the conversation text.

## Requirements and sizing

* Linux host with Docker, x86_64 or arm64, public DNS name and port 443 (or any port the PBXs can reach).
* CPU: about **2 concurrent calls per vCPU** keep the answer delay p95 near 1.2 s (speech recognition is
  the bottleneck: ~340 ms per 2-4 s phrase on one core). Set `VA_MAX_CALLS` accordingly; connections over the
  limit receive HTTP 503 before allocating a session; the PBX routes the call to its fallback number.
* RAM: ~1.5 GB plus ~60 MB per concurrent call; the Silero voices add ~300 MB (torch). Disk: ~1.6 GB for the
  models volume.
* Measured on 2 vCPU (Cascade Lake), one call: answer after end of speech p50 ~615 ms, p95 ~860 ms;
  gpt-oss-120b on Cloud.ru first token p50 ~310 ms. PBX-to-runtime RTT of a few ms is plenty.

## Deploy

```bash
cd ModuleVoiceAgent-runtime
cp .env.example .env && chmod 600 .env        # LLM key, TLS paths, limits
mkdir -p config tls
cp config/tenants.example.json config/tenants.json
docker compose build
docker compose run --rm runtime download-models   # optional: otherwise the first start downloads them
docker compose up -d
curl -s https://voice.example.com/health
```

### TLS

Asterisk connects with `wss://`, the PBX module with `https://`. Put `fullchain.pem` and `privkey.pem`
into `./tls` (or set `VA_TLS_DIR`):

* **Let's Encrypt**: `certbot certonly --standalone -d voice.example.com`, then link
  `/etc/letsencrypt/live/voice.example.com/{fullchain,privkey}.pem` into `./tls` (the container user
  uid 10002 must be able to read them) and `docker compose restart runtime` after each renewal
  (`--deploy-hook`). Keep "Verify TLS certificate" on in the module settings.
* **Self-signed** (lab only): `openssl req -x509 -newkey rsa:2048 -nodes -days 825 -keyout tls/privkey.pem
  -out tls/fullchain.pem -subj /CN=voice.example.com -addext subjectAltName=DNS:voice.example.com` and turn
  "Verify TLS certificate" off in the module settings.
* Behind a TLS-terminating reverse proxy, leave `VA_TLS_CERT`/`VA_TLS_KEY` empty, set
  `VA_TRUSTED_PROXY=true` and `VA_PUBLIC_BIND=127.0.0.1`, and make sure the proxy passes WebSocket
  upgrades on `/media` with the `media` subprotocol. Plain HTTP startup requires this explicit opt-in.

### Register a PBX

Each PBX has an id and a token generated by the module. In MikoPBX, `GET /pbxcore/api/v3/module-voice-agent/settings`
(or the settings page) shows a `registration` entry; add it to `config/tenants.json`. The raw token is
shown only in the response to token rotation, so copy it then if needed:

```json
{"tenants": [{"id": "pbx-1a2b3c4d5e6f", "name": "ACME", "token_sha256": ["<hex>"], "max_calls": 4, "max_agents": 5}]}
```

`max_calls` and `max_agents` are optional per-PBX limits (defaults: `VA_MAX_CALLS_PER_TENANT`,
`VA_MAX_AGENTS_PER_TENANT`).

Only the SHA-256 of the token is stored here (`voice-agent-runtime hash-token <token>` computes it). The
file is re-read automatically. For a token rotation list both hashes, rotate on the PBX, then remove the
old hash.

## Voices

| Id | Engine | Voice | License |
|---|---|---|---|
| `ru_RU-dmitri-medium`, `ru_RU-denis-medium` | Piper | Дмитрий, Денис (male) | voices CC0; `piper-tts` package GPL-3.0 |
| `silero-ekaterina`, `silero-oksana`, `silero-zinaida` | Silero v5_cis_base | Екатерина, Оксана, Зинаида (female) | MIT (model and silero-stress) |
| `silero-roman`, `silero-eduard` | Silero v5_cis_base | Роман, Эдуард (male) | MIT |

Other Russian Piper voices (irina: unclear license, ruslan: CC BY-NC-SA) and the Silero v5_ru voices
(CC BY-NC) are not shipped. Silero is 3-4 times faster than Piper (RTF ~0.035 vs ~0.12 on one server core, a
phrase in 0.16-0.22 s) and puts stress with silero-stress; it needs torch (~300 MB more RAM). The model
(`v5_cis_base.pt`, 87 MB) is downloaded from models.silero.ai into the models volume and checked by SHA-256.

Both engines speak Russian only. Latin words are transliterated by the text normalizer ("Zoom" -> "зум",
"TP-Link" -> "ти пи линк"), which suits brand names, not English sentences.

Stress: Silero voices place stress automatically (silero-stress); a wrong one is fixed in the agent texts with
"+" before the stressed vowel ("МИК+О", "з+амок") in the greeting, company name, knowledge base or directory. The
model is told to keep the mark when it says the word. Piper voices and speech-recognition hints ignore the mark;
any other "+" ("+7 999") is not a stress mark.

A bundle may name any voice: one this runtime does not load is replaced by `VA_DEFAULT_VOICE` (the PUT answer
says `"voice_fallback": true`), so a PBX module with newer voices keeps working with an older runtime.
`GET /v1/voices` lists the loaded voices for the module's voice picker, `GET /v1/voices/{id}/sample` returns an
8 kHz WAV sample (the standard phrase, or `?text=` up to 300 characters, e.g. the agent greeting).

## Speech recognition

**Incremental recognition.** GigaAM is not streaming and its time grows with the audio (~340 ms for a
2-4 s phrase, 500-700 ms for 5-10 s on one server core), so a long question used to be recognized as a whole
after the caller stopped. Every speculative turn (120 ms of silence) recognizes only the audio after the last
committed boundary; when the pause reaches `VA_STT_CHUNK_PAUSE_MS` that piece is committed and later
speculations start after it. At the end of the turn only the last phrase is left, and each second of audio is
recognized about once (the old way re-recognized the whole turn at every pause). Pieces shorter than
`VA_STT_CHUNK_MIN_MS` are not committed (too little context). Turn-taking (120 ms speculation, 600/300 ms
turn end, barge-in) is unchanged. Measured on an Apple M2 core with GigaAM v3: a 10.5 s question with two
pauses 1693 -> 1337 ms after the last speculation, a 4 s phrase 657 -> 176 ms; CPU per turn -31% and -48%.
The pieces are joined with spaces, so the model's sentence punctuation may appear at a cut ("Здравствуйте.
Соедините ...").

**Hotwords.** Terms from the bundle (`hotwords`, then company name, directory names and aliases,
departments, queue names, knowledge topics, names in «quotes» and abbreviations from the rules and answers;
at most 300) bias GigaAM's greedy decoder with a capped bonus that starts at the third letter of a term and
never makes the model write where it wrote nothing (the approach of LocalSTTWorker). Abbreviations whose
first letter telephony lost ("ТС" for "АТС") are restored after recognition when exactly one known
abbreviation matches; other words are never rewritten.

## Usage metering

Per PBX (tenant) and agent and per UTC day of the call start: `calls`, `connected_seconds`,
`agent_speech_seconds` (audio sent to the caller), `caller_turns` (answered turns), `llm_requests`,
`llm_input_tokens`, `llm_output_tokens`, `llm_estimated_requests`, `tts_characters` (characters of the
phrases played) and `fallbacks`. LLM tokens include speculative and hedged requests that were dropped (the
provider charged them); without usage in the stream they are estimated as characters / 3.2 and the request
is counted in `llm_estimated_requests`. Only these aggregates are written to disk (`VA_USAGE_DB`, SQLite in
the `data` volume): no numbers, call ids or texts. `GET /v1/usage?from=YYYY-MM-DD&to=YYYY-MM-DD` (default the
last 31 days, at most 366) returns the calling PBX's `days` (per day and agent), `agents` and `total`;
`/metrics` exposes all-time totals as `voice_agent_usage_<counter>_total{tenant="..."}`.

## API

| Method | Path | Auth | Purpose |
|---|---|---|---|
| GET | `/health` | none / Bearer / Operator | public status only; a PBX Bearer receives version, latency and **its own** calls, limits and counters; the operator token receives everything with a per-tenant breakdown |
| GET | `/metrics` | Operator | Prometheus metrics (series labelled by `tenant`) |
| GET | `/v1/usage?from=&to=` | Bearer | this PBX's usage counters per UTC day and agent |
| GET | `/v1/voices` | Bearer | loaded voices (id, name, gender, engine) and the default voice |
| GET | `/v1/voices/{id}/sample?text=` | Bearer | voice sample, `audio/wav` 8 kHz; 404 `unknown_voice` |
| GET | `/v1/agents` | Bearer | bundles of this PBX (heartbeat) |
| PUT | `/v1/agents/{id}` | Bearer | load a bundle (RAM only; 413 above the prompt size limit) |
| DELETE | `/v1/agents/{id}` | Bearer | forget a bundle |
| GET | `/v1/calls/{call_id}/result?wait=2` | Bearer | retryable call result; 202 while the call is active |
| DELETE | `/v1/calls/{call_id}/result` | Bearer | acknowledge committed result; idempotent 204 |
| GET | `/media` | Basic | chan_websocket media (subprotocol `media`) |
| GET | `/ready` | none | 200 `ready` once taken over from the peer and warm; 503 `starting` / `draining` (load balancer check) |
| GET | `/internal/handoff` | Operator | every bundle as the PBX sent it, for the next instance |
| GET, DELETE | `/internal/calls/{tenant}/{call_id}/result` | Operator | this instance's call result (the peer forwards here) |
| POST, DELETE | `/internal/drain` | Operator | stop / resume taking new calls; active calls and results go on |

The PBX `/health` answer also carries `boot_id` (a new value for every start: the module pushes its bundles at
once) and `capabilities` (`result_ack`, `usage`, `voices`, `voice_samples`, `off_hours`, `hotwords`, `ready`,
`handoff`).

Bearer = `Authorization: Bearer <pbx_id>.<token>`; Operator = `Authorization: Bearer <VA_ADMIN_TOKEN>`;
Basic = the websocket_client username/password. A PBX never sees another PBX's numbers.

## Scaling to many PBXs

Agent bundles, active calls and unclaimed results live in the RAM of one process, so instances cannot share
PBXs behind a load balancer: a result would be asked for on an instance that never saw the call. Scale out by
**sharding**: every instance has its own DNS name (`voice-1.example.com`, `voice-2.example.com`, ...) and every
PBX is pointed at exactly one of them (its runtime URL in the module settings) and listed in that shard's
`tenants.json`. Moving a PBX = add it to the new shard, change the URL on the PBX, remove it from the old one.
`VA_TENANTS_FILE` may be a directory with one `*.json` per PBX (a broken file disables only that PBX).
`terraform/` deploys such shards to Yandex Cloud.

## Development

```bash
python3.12 -m venv .venv && . .venv/bin/activate
pip install -e '.[dev]'          # add '.[speech]' to run the service itself
pytest && ruff check src tests
```

`tests/test_speech_models.py` runs GigaAM and Silero for real when they are already in `VA_MODELS_DIR`
(default `~/.cache/va-models`; `voice-agent-runtime download-models` fills it) and is skipped otherwise;
speech comes from Piper on Linux and from macOS `say` (Milena) on a Mac.

The PHP client integration test also uses a sibling `Extensions/ModuleVoiceAgent` checkout. Set
`VOICE_AGENT_MODULE_DIR` to the module checkout path when it lives elsewhere; the test is skipped when the
checkout is unavailable.

## CI/CD (GitHub Actions)

`.github/workflows/ci-cd.yml`: every push and pull request runs ruff and the tests (without the speech models;
their tests are skipped). A push to `main` then updates the server: the code directories are mirrored over SSH
(`.env`, `tls/`, `config/` and the model volume on the server are never touched) and `scripts/deploy.sh` builds
the image and switches to it (`--build --restart` by default: a ~35 s pause at a moment without calls; set the
variable `VA_DEPLOY_ARGS=--build` for blue-green without a pause when the host has RAM for two runtimes).
`develop` is the working branch: tests only. Deploys never overlap and are never cancelled halfway.

Secrets: `VA_DEPLOY_HOST`, `VA_DEPLOY_USER`, `VA_DEPLOY_SSH_KEY` (a deploy-only key of that user),
`VA_DEPLOY_KNOWN_HOSTS` (`ssh-keyscan <host>`). Variables: `VA_DEPLOY_PATH` (default `~/voice-agent/runtime`),
`VA_DEPLOY_ARGS`. The deploy runs in the `production` environment, where reviewers can be required.

## Updates without downtime (blue-green)

`compose.bluegreen.yaml` runs Caddy in front of two runtime services, `runtime-blue` and `runtime-green`;
normally only one of them runs. `scripts/deploy.sh --build` builds the image and updates:

1. The other color starts next to the running one. Before it reports ready on `/ready`, it takes the agent
   bundles over from the running instance (`VA_PEER_URL`, operator token; memory to memory, nothing on disk)
   and synthesizes their greetings, so its first call is as fast as any.
2. Caddy checks `/ready` every second and sends new connections to the first ready runtime. Every call is its
   own WebSocket, so active calls stay where they started.
3. The old instance is drained (`voice-agent-runtime drain`): it takes no new calls, its active calls end
   normally (up to `VA_DEPLOY_DRAIN_WAIT`, 31 minutes), and the PBXs collect their results. A PBX asks the new
   instance, which forwards results and acknowledgements it does not know to the old one. Then it is stopped.

If the new instance does not become ready (`VA_DEPLOY_READY_TIMEOUT`, 15 minutes), it is stopped and the old
one keeps serving; the previous image stays tagged `voice-agent-runtime:previous` for a rollback
(`scripts/deploy.sh --image voice-agent-runtime:previous`). Both instances share the models and `data`
volumes (usage counters are added up, not overwritten).

Requirements: `VA_ADMIN_TOKEN` in `.env` (the instances authenticate each other; it never reaches the PBXs),
TLS files readable by uid 10002 (as for the single container), and RAM for two runtimes during the update:
the script refuses below `VA_DEPLOY_MIN_FREE_MB` (2300) of available memory. On a smaller host
`scripts/deploy.sh --build --restart` waits for a moment without calls, stops the old instance and starts
the new one: calls during the start (about a minute) go to the PBX fallback numbers. `VA_PUBLIC_BIND`
defaults to `127.0.0.1` as in `compose.yaml`; set it to `0.0.0.0` when the PBXs connect to this host directly.
A renewed certificate: `docker compose -f compose.bluegreen.yaml exec proxy caddy reload --config /etc/caddy/Caddyfile`
(active calls are kept).

Moving from `compose.yaml`: add `VA_ADMIN_TOKEN` (and `VA_PUBLIC_BIND=0.0.0.0` if the port was public),
`docker compose stop runtime` at a quiet moment, then `scripts/deploy.sh --build`; the PBXs push their bundles
within seconds (the module notices the new `boot_id`).

The PBX module (from this version on) asks `/health` every 10 seconds and pushes its bundles as soon as the
`boot_id` changes, and after a call that found no bundle, so a plain restart heals within seconds too.

### Result delivery and upgrades

Deploy this runtime before the matching PBX module. `GET .../result` retains the result, and
`DELETE .../result` acknowledges the PBX transaction. Unacknowledged results expire independently of
PBX reads (cleanup runs at most every 30 seconds). A runtime restart discards RAM data.
The container healthcheck uses `VA_LISTEN_PORT` and the configured TLS mode; `--url` overrides it.
